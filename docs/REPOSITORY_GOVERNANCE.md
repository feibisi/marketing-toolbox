# Repository Governance

> [CX] 记录日期：2026-08-13  
> 本文定义 Marketing Toolbox 长期维护方式，不证明任何仓库设置、保护规则、发布或部署已经在 FeiCode/生产环境启用。

## 1. 仓库职责

本仓库是 Modiqi Marketing Toolbox 的代码、公开数据契约、测试、产品文档和可复核审计资料的单一维护入口。它是独立应用，不是 `modiqi.com` WordPress 主题、插件或子模块。

`modiqi.com` WordPress 主站负责搜索内容、品牌说明、活动、服务落地和转化入口。两者只通过公开、版本化的工具目录和链接契约协作：

- 主站链接到工具或工作流入口；
- 工具箱可在适当节点链接回主站的说明或服务页面；
- 不共享登录态、业务数据库、客户资料或浏览器画布数据；
- WordPress 不可成为工具运行、保存、导出或打印的前置条件；
- 主站不可把“计划页面”或“候选工具”写成已经上线的事实。

线上发布、DNS、CDN、WordPress 内容发布和分析平台配置由各自权威系统管理，不因代码合并自动发生。

## 2. 事实来源

| 事实 | 单一来源 | 维护要求 |
|---|---|---|
| 工具 ID、路径、标题和等级 | `data/tools.json` | 由同步脚本生成并校验 |
| 核心工具与工作流 | `data/workflows.json`、`data/core-tool-contracts.json` | 6 条工作流恰好覆盖 30 个核心工具 |
| 核心 readiness | `data/core-tool-readiness.json` | 由脚本生成；不能手工拔高状态 |
| 项目数据合同 | `data/project-context.schema.json` 及对应测试 | 版本化并提供兼容/迁移验证 |
| 发布面和运行模型 | `docs/ARCHITECTURE.md` | 与代码变化同步 |
| 质量门禁 | `docs/QUALITY_GATES.md`、`package.json` | 命令和实际脚本一致 |
| 版本变化 | 根 `CHANGELOG.md` | 只记录已合入的源代码事实 |
| 视觉布局结果 | `reports/visual-layout-audit.json` | 记录测量范围和时间 |

根 `CHANGELOG.md` 从当前长期治理开始记录项目级版本；`docs/CHANGELOG.md` 保留历史设计系统记录，不作为当前发布状态证明。

## 3. 角色与决策

长期至少需要明确以下责任，可由少数人兼任，但不能无人负责：

- **产品负责人**：核心工作流、支持分层、用户价值和停止条件；
- **工程维护者**：架构、数据迁移、依赖、合并和版本候选；
- **内容/方法负责人**：方法来源、业务公式、示例和事实/假设边界；
- **设计负责人**：设计令牌、可访问性、响应式和打印规范；
- **安全/隐私负责人**：导入、持久化、依赖、漏洞和数据边界；
- **发布负责人**：授权、目标环境、回滚和发布后验证。

尚未指派具体人员时，相关发布门禁保持未满足，不能用代理、自动化或仓库权限替代业务责任。

以下改动需要至少一名对应责任人评审：核心工具集合、工具 ID/路径、项目 schema、数据迁移、共享运行时、依赖、导入清洗、公开承诺、许可和发布流程。影响安全或数据兼容的改动应增加专项评审。

## 4. 分支与合并

- `main` 表示最新可维护源码，不自动表示生产版本。
- 日常工作使用短期 `feature/`、`fix/`、`docs/`、`test/` 或 `chore/` 分支。
- 通过合并请求评审，避免直接向 `main` 写入未审查的功能或迁移。
- 平台条件允许时，应为 `main` 配置禁止强推、要求评审和要求质量检查；在平台上实际验证前只能写“待配置”。
- 不保留长期环境分支；环境状态由部署记录和不可变版本标记证明。
- 发现并行改动时合并已有 WIP，不得通过重置或大范围格式化覆盖他人工作。

合并请求必须说明目的、影响面、验证、样本、兼容性、隐私/安全影响、回滚和已知债务。合并者不得仅凭 HTTP 200、页面截图或旧测试结果批准业务正确性。

## 5. 版本和发布

采用 `MAJOR.MINOR.PATCH`：

- **MAJOR**：不兼容的项目数据、工具 ID、公开契约或运行时变化；
- **MINOR**：向后兼容的新能力、核心工具深化或工作流输出；
- **PATCH**：向后兼容的缺陷、文档或维护修复。

版本流程：

1. 冻结候选范围并更新根 `CHANGELOG.md`；
2. 使用锁文件安装依赖，执行 `npm run test:quality`；
3. 核心正式发布还需 `npm run check:release-readiness`、真实业务样本和手动浏览器/打印抽样；
4. 按 `docs/RELEASE_CHECKLIST.md` 检查秘密、产物、授权、备份和回滚；
5. 只有发布负责人获授权后才能创建版本标记或部署；
6. 发布后记录提交、产物校验、目标环境、样本、时间和回滚结果。

版本号、Git 标签、FeiCode Release、合并或本地门禁各自是不同事实。缺少实际目标环境验证时只能写“候选”，不能写“已上线”。

### FeiCode 仓库生命周期

首次推送已经完成；以后不得把 `scripts/push_feicode_initial.sh` 当作日常 push 包装器。仓库身份、SSH principal、权限证据、凭据事故处理和日常协作边界统一见 [`FEICODE_REPOSITORY_OPERATIONS.md`](FEICODE_REPOSITORY_OPERATIONS.md)。

只有在全新的、尚未推送的同名空仓库恢复场景中，才可运行：

```bash
scripts/push_feicode_initial.sh
```

脚本只接受无凭据的 `ssh://git@feicode.com/Modiqi-com/marketing-toolbox.git`，先验证仓库身份、公开可见性、工作区清洁和秘密扫描，再推送 `main`，最后逐项核对远端 SHA、默认分支与非空状态。它通过 `GIT_CONFIG_GLOBAL=/dev/null` 隔离全局 URL rewrite，避免全局凭据被展开到诊断输出。

仓库不存在、可见性不符、远端不是 `main` 或 SHA 不一致时均失败关闭；不得把 SSH 认证成功当作建仓或推送成功。

## 6. 质量与债务

`npm run test:quality` 是合并前的统一自动化门禁。业务公式、真实样本、Safari/其他浏览器、打印审阅和内容方法来源需按改动另行补充。零真实样本不构成业务 `PASS`。

债务必须包含：影响范围、证据、负责人或待指派状态、处理门槛和复核日期。不得通过放宽断言、隐藏内容、移除测试或把 error 改成 warning 来关闭债务。

当前 715 个 CSS 设计令牌 warning 是已记录债务，新增或修改 CSS 不应增加基线。30 个核心工具的 `smoke` 状态也不能被解读为正式支持或发布完成。

## 7. 安全、隐私与依赖

- 不提交密钥、生产配置、客户资料、测试导出或私人截图。
- 浏览器依赖固定版本并同步至本地 `shared/vendor/`；升级必须评审锁文件、字节同步和运行回归。
- schema、导入、清洗和 `localStorage` 变更必须评审迁移、降级和恶意输入。
- 安全报告遵循根 [`SECURITY.md`](../SECURITY.md)，公开记录不包含可利用细节。
- 账户、云同步、协作、服务端存储只有在权限、留存、审计、删除和部署模型获批后才可进入实现。

## 8. 文档与内容治理

- 架构、数据、质量、产品定位和路线各自保持单一来源，其他文档使用链接引用。
- 对外内容区分事实、判断、假设、计划和已发布状态；工具数量不等于支持深度。
- 方法、统计、案例和效果主张需要来源、复核日期和负责人；合成示例必须显式标注。
- 主站的工具页、文章和落地页属于营销内容，不复制或接管工具运行逻辑。
- 删除、重命名工具或页面前先完成引用、兼容、搜索入口和旧导出的影响审计。

## 9. 定期维护

建议按以下节奏建立维护记录，具体负责人和日期需另行指派：

- 每次合并：相关测试、清单同步、变更记录和秘密检查；
- 每月：依赖候选、404/引用、浏览器烟测、设计债务和安全报告盘点；
- 每季度：30 个核心工具 readiness、业务样本、方法来源、内容表现和扩展工具升降级；
- 每个版本：完整门禁、发布检查、产物校验和回滚演练。

维护频率是治理目标；没有实际执行记录时不得写成已完成。
