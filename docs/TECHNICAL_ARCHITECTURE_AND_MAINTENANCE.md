# Technical Architecture and Maintenance

> [CX] 版本：1；日期：2026-08-13  
> 状态：当前事实与长期技术约定。候选能力不代表已实现或已部署。

## 1. 当前技术基线

Marketing Toolbox 当前是无构建步骤的静态 Web 应用：HTML、共享 CSS、共享 JavaScript 和版本化 JSON 清单组成 144 个工具页面。标准开发入口为本地 HTTP 服务；工作流依赖 `fetch()`，不支持直接通过 `file://` 运行。

| 领域 | 当前实现 |
|---|---|
| UI | 原生 HTML/CSS/JavaScript，共享设计令牌与运行时 |
| 工具目录 | `data/tools.json`，144 条记录 |
| 工作流 | `data/workflows.json`，6 条工作流覆盖 30 个核心工具 |
| 核心合同 | `data/core-tool-contracts.json` 与 `data/core-readiness.json` |
| 项目数据 | project schema v2，浏览器 origin 内 `localStorage` |
| 证据数据 | `fact`、`assumption`、`to_verify` 及来源/负责人/复核状态 |
| 前端依赖 | 固定版本、本地供应，不在发布页从 CDN 执行 |
| 输出 | JSON、图片、打印/PDF，具体支持以页面验收为准 |
| 验证 | 清单、schema、依赖、HTML、JS、引用、表单、CSS、Playwright 与布局检查 |

详见 [`ARCHITECTURE.md`](ARCHITECTURE.md)、[`PROJECT_DATA_MODEL.md`](PROJECT_DATA_MODEL.md) 和 [`QUALITY_GATES.md`](QUALITY_GATES.md)。

## 2. 长期架构原则

1. **静态与 local-first 是默认。** 没有经验证需求时不增加应用服务器、数据库或账户系统。
2. **渐进增强。** 内容、输入和主要导航在脚本失败时应尽可能保持可理解；高级计算明确显示不可用状态。
3. **共享能力集中。** 保存、证据、交接、导入导出、清洗、打印和可访问性进入共享模块，不复制到 144 个页面。
4. **业务逻辑可测试。** 公式、分类、完成规则和迁移从 DOM 事件中分离为确定性模块。
5. **契约优先。** 工具、工作流、项目、证据、报告和公开目录使用有版本 schema。
6. **依赖最少且可替换。** 固定版本、记录许可与来源、禁止未审查的远程执行代码。
7. **发布与部署分离。** 测试通过形成候选；域名、托管、缓存和公开发布需要独立授权与线上验证。

## 3. 推荐的模块演进

不建议立即用大型框架重写 144 个页面。先在现有静态结构中建立边界：

```text
shared/
├── js/
│   ├── project-store.js       # 项目与迁移
│   ├── evidence-store.js      # 候选：证据校验和来源
│   ├── workflow-handoff.js    # 候选：显式、可追溯交接
│   ├── report-model.js        # 候选：仅汇总合格结论
│   └── core.js                # 通用 UI 与兼容入口
├── css/                       # 设计令牌、组件、打印
└── vendor/                    # 已审计固定版本依赖
data/
├── tools.json
├── workflows.json
├── core-tool-contracts.json
├── core-readiness.json
├── project-schema.json
└── public-catalog.json        # 候选：主站公开目录契约
```

当共享模块具有稳定测试和 API 后，再评估 TypeScript、模块打包或组件框架。采用新栈必须证明以下至少一项：显著减少重复缺陷、提升类型/迁移安全、改善可访问性、降低发布复杂度或解决已验证协作需求。重写本身不是产品进度。

## 4. 数据资产体系

### 4.1 数据分类

| 类别 | 示例 | 真源与处理 |
|---|---|---|
| 产品清单 | 工具、tier、分类、路径 | 仓库版本化 JSON，可公开 |
| 方法合同 | 问题、输入、公式、完成规则 | 仓库评审；领域负责人批准 |
| 工作流合同 | 顺序、交接、输出 | 仓库评审；产品与领域共同批准 |
| 项目运行数据 | 目标、约束、画布、证据 | 用户浏览器本地；用户主动导出 |
| 公开内容目录 | marketing URL、状态、reviewer | 版本化契约；WordPress 为发布真源 |
| 匿名行为事件 | 打开、推进、导出类型 | 仅批准属性、最小保留和同意策略 |
| 业务真源 | 线索、合同、项目、收入、复购 | 独立获授权系统；不得写入本仓库 |
| 研究样本 | 测试 fixture、脱敏案例 | 标注真实/脱敏/合成、授权与用途 |

### 4.2 数据质量规则

- 稳定 ID 不随标题、翻译或 URL 改变；
- JSON schema 明确必填字段、枚举、大小和未知字段策略；
- 生成清单必须可重复，检查模式拒绝漂移；
- 事实、假设和待验证项不得在聚合时丢失类型；
- 真实、脱敏、合成和演示数据必须显式标注，零真实样本不得写业务 `PASS`；
- 公开 URL 记录发布状态，`planned`/`draft` 不能被消费方当作线上可用；
- 删除、合并和退役保留迁移映射，避免项目导入失去工具引用。

### 4.3 数据迁移

每个持久化 schema 采用整数版本。兼容变更提升次要文档版本；破坏性变更提升 schema 主版本，并提供：

1. 旧版本读取和验证；
2. 确定性迁移函数；
3. 原始数据回滚副本或无损导出路径；
4. 正常、缺失、非法、超大和重复输入 fixture；
5. 迁移后重新导入和报告生成测试；
6. 明确的停止支持日期，不静默删除本地数据。

## 5. 隐私与安全架构

- 浏览器本地并不等于无风险：共享设备、浏览器同步、扩展、截图和导出文件都可能暴露数据；
- 页面明确提醒不要输入密码、API 密钥、支付信息、不必要的个人敏感信息或未经授权的客户资料；
- JSON 导入验证版本、MIME/扩展、大小、结构和值类型，拒绝原型污染键和可执行内容；
- HTML/富文本输出在进入 DOM、打印、图片和报告前使用统一清洗策略；
- 外部链接和跨域导航不附带项目内容，UTM 参数不得包含个人或业务机密；
- 第三方脚本在引入前记录目的、数据流、许可、完整性/固定版本、故障降级和移除方案；
- 若未来增加云端功能，必须先完成认证、授权、租户隔离、传输/静态加密、备份、删除、审计和事件响应设计。

## 6. 可访问性、响应式与打印

核心工具的发布验收至少覆盖：

- 语义标题、标签、说明、错误关联和可见焦点；
- 全键盘路径、焦点顺序、弹层关闭和拖拽替代操作；
- 缩放、窄屏、长内容、中文/英文混排和系统字体回退；
- 颜色对比、非颜色状态提示、减少动画偏好；
- A4/Letter 分页、表头、来源、状态、复核日期和不截断关键结论；
- 桌面、移动和核心打印截图中的重叠、溢出、遮挡和错位。

布局检查通过只证明被检查视口没有规则命中的视觉故障，不代替人工设计评审或真实内容极值测试。

## 7. 测试金字塔与发布门禁

### 每次变更

- 格式、语法和本地引用；
- 受影响 schema、清单生成和漂移检查；
- 受影响业务逻辑单元/fixture；
- 不新增秘密、生产导出、客户资料或超大二进制。

### 核心工具变更

- 一个有效样本和一个边界/非法样本；
- 持久化、刷新、重置、显式交接和导入导出；
- 键盘、移动、打印和报告映射；
- 领域负责人对方法、术语和预期结果的复核。

### 发布候选

运行项目定义的完整质量门禁，记录命令、时间、提交、浏览器、样本数和结果。`PASS` 必须注明检查范围和样本来源；未运行项标记 `SKIP`，环境或权限阻塞标记 `BLOCKED`，失败不得用旧结果覆盖。

线上发布另需验证目标 URL、缓存版本、关键资源、错误日志、隐私/分析配置和回滚；本地测试不能证明线上部署。

## 8. 版本与发布策略

建议采用 SemVer 管理工具箱发布：

- `MAJOR`：持久化数据、公开目录或核心交互发生不兼容变化；
- `MINOR`：新增向后兼容工具、工作流能力或重要方法；
- `PATCH`：缺陷、文案、样式、测试或不改变契约的修复。

每个发布候选记录：提交 SHA、版本、工具/工作流清单摘要、schema 版本、依赖清单、质量结果、已知问题、迁移、回滚和批准人。不要直接覆盖唯一线上目录；托管方案应支持不可变版本和可回退的当前指针，但具体部署设计需在选定平台后另行批准。

## 9. 依赖与供应链维护

1. 依赖只因明确功能使用而存在，未使用依赖移除；
2. 锁文件提交，供应文件由脚本从锁定依赖可重复生成；
3. 每月至少检查安全公告和过期版本，高危问题按影响加急；
4. 升级单独提交，记录上游变更并运行完整浏览器/打印回归；
5. 记录直接依赖的许可、来源和替代方案；
6. 禁止把令牌、私有注册表凭据或开发机路径写入配置和构建产物；
7. CI/Forgejo Action 使用固定版本或已审核提交，不默认执行不受控第三方代码。

## 10. 维护节奏

| 周期 | 工作 |
|---|---|
| 每次变更 | 受影响测试、清单漂移、敏感信息检查、文档同步 |
| 每周 | 新增缺陷分级、核心工作流回归、失败门禁处理 |
| 每月 | 依赖与安全检查、移动/打印抽样、内容目录同步 |
| 每季度 | 30 个核心 readiness 复核、114 个扩展晋级/合并/退役、可访问性和隐私复核 |
| 每半年 | 架构债务、浏览器支持、数据迁移恢复演练、服务与内容指标评审 |
| 每年 | 项目章程、许可、第三方数据流、保留策略和灾难恢复审查 |

缺陷优先级以数据损坏/泄露、错误业务结论、无法恢复、核心工作流阻塞、可访问性阻塞、布局/文案问题依次评估。修复后必须增加能捕获该缺陷的回归证据。

## 11. 浏览器与平台支持

正式支持矩阵应在首次公开发布前确认。默认候选是当前与前一个主要版本的 Chromium、Firefox 和 Safari，以及主流 iOS/Android 浏览器；实际支持必须由自动化和人工样本证明。

对不支持的 API 提供功能检测和可理解降级，不能仅依赖 user-agent。图片/PDF、剪贴板、文件保存和打印在不同浏览器差异较大，应逐项声明支持状态，不使用笼统的“全平台可用”。

## 12. 何时评估新技术栈

出现以下可度量条件之一时，才发起架构提案：

- 共享字段和状态同步缺陷持续跨多个工具重复；
- 模块边界无法通过现有 ES modules 和 schema 保证；
- 构建时间、页面体积或运行性能超过已批准预算；
- 多语言、组件可访问性或测试维护成本无法在现有结构控制；
- 经验证的多人协作需求必须使用服务端。

提案必须比较“继续模块化现有静态应用”“逐页迁移”“整体重写”三种路径，包含迁移顺序、双运行期、数据兼容、回滚、团队能力和总维护成本。未经该评审，不将框架流行度作为重写依据。

## 13. 未完成与决策门

以下仍是待建设或待确认事项，不得写成当前能力：

- 30 个核心工具尚需从当前 readiness 逐级完成 fixture、领域复核和 release；
- 共享 evidence、handoff 和 report 模块需按工作流实现并测试；
- 工具箱公开域名、托管、CI、监控和版本回滚方案尚需单独授权；
- WordPress 公开目录的传输方式、实际 URL 和发布工作流尚需与主站核对；
- 分析供应商、同意方式、数据保留和跨域归因需隐私评审；
- 账户、云同步和多人协作保持候选，未进入默认开发范围。
