# modiqi.com Growth and Content System

> [CX] 版本：1；日期：2026-08-13  
> 适用范围：`modiqi.com` WordPress 主站与独立 Marketing Toolbox 之间的公开获客、内容、导航和测量关系。本文不是线上页面已存在的证明。

## 1. 目标与分工

`modiqi.com` 是莫蒂奇的品牌、内容、获客和服务转化主站；Marketing Toolbox 是独立运行的工具产品。主站回答“我遇到什么问题、应采用什么方法、莫蒂奇能如何帮助”，工具箱回答“如何实际完成分析、保留证据并形成交付物”。

两者的目标链路是：

1. 搜索、社交、广告或转介绍访问主站；
2. 访客从问题、方法、行业或工作流入口发现合适工具；
3. 工具箱在不要求 WordPress 登录的情况下完成任务；
4. 用户在帮助、完成、导出、工作流或报告语境中可返回主站；
5. 有进一步需求的用户进入咨询、培训或项目服务页面。

## 2. 内容架构

建议的主站信息架构如下。路径是内容契约候选，发布前需核对现有 WordPress URL、canonical 和重定向规则。

| 内容类型 | 候选路径 | 主要意图 | 规模策略 |
|---|---|---|---|
| 工具目录 | `/tools/` | 浏览和筛选全部工具 | 1 个目录入口 |
| 核心工具资源页 | `/tools/{tool-slug}/` | 解释业务问题、方法、输入、输出和边界 | 30 个完整页面 |
| 扩展工具条目 | `/tools/{tool-slug}/` | 可发现、可索引或按策略 noindex 的简明目录项 | 114 个轻条目，按证据晋级 |
| 工作流专题 | `/workflows/{workflow-slug}/` | 从业务目标进入一组有顺序的工具 | 6 个专题页 |
| 问题型文章 | `/insights/{article-slug}/` | 回答真实问题、案例、方法或比较意图 | 首批 20–30 篇，后续按集群演进 |
| 服务落地页 | `/services/{service-slug}/` | 承接咨询、培训或项目服务 | 约 6 个，以服务/项目包为单位 |

### 不采用“一工具三页”

不为每个工具机械创建“文档 + 文章 + 落地页”。这会制造重复意图、内容稀释、canonical 冲突和持续维护负担。

- **工具资源页**是方法和使用入口，一工具一条公开内容记录；
- **文章**围绕问题、场景、案例和搜索意图组织，可关联多个工具；
- **落地页**围绕工作流、项目包和服务结果组织，可关联多个工具与文章。

## 3. 核心工具资源页标准

30 个核心工具各自需要完整资源页，最低包含：

1. 主要业务问题与适用对象；
2. 不适用边界和常见误用；
3. 开始前所需输入与来源；
4. 方法、公式、分类或判断依据；
5. 可评审输出和完成标准；
6. 一个经核对的示例，明确标识真实、脱敏或合成来源；
7. 常见错误、边界值和复核清单；
8. 上游、下游和所属工作流；
9. 进入独立工具箱的主操作；
10. 作者、领域审阅人、首次发布和最近复核日期；
11. 相关问题文章、工作流和服务；
12. 适合页面类型的结构化数据、canonical、标题和摘要。

核心资源页不得声称某方法已经过客户验证，除非有可追溯且获准公开的样本。工具处于 `smoke` 或 `contract` 时，应避免使用“已验证”“保证”“准确预测”等公开承诺。

## 4. 扩展工具条目和晋级

114 个扩展工具先以简明目录条目存在，最低字段为：名称、主要问题、分类、支持等级、适用对象、工具入口、相关核心工具和更新时间。

扩展条目满足以下证据后才晋级为完整资源页：

- 有独立且稳定的搜索或用户问题，不与核心页重复；
- 工具具有可说明的方法、输入、输出和不适用边界；
- 有持续使用、工作流贡献或服务助攻证据；
- 有明确内容负责人和复核周期；
- 页面能够提供超出工具界面自身的原创说明或示例。

薄弱、重复或无法维护的条目可以 `noindex`、合并到目录或退役，不能只为保持“144 个页面”而公开索引。

## 5. 文章问题集群

文章按用户问题和决策阶段组织，而不是按工具名称逐个生成。建议的首批集群：

| 集群 | 典型问题 | 关联工作流 |
|---|---|---|
| 战略选择 | 如何识别战略矛盾、判断优先级、把战略转成路线图 | 战略对齐 |
| 受众与定位 | 如何选择细分市场、验证痛点、形成差异化定位 | 受众与定位 |
| 品牌叙事 | 如何统一价值主张、品牌信息和销售表达 | 品牌叙事 |
| 内容运营 | 如何建立内容支柱、编辑节奏和复用体系 | 内容运营 |
| 获客与成交 | 如何诊断漏斗、渠道、线索质量和销售协同 | 获客与成交 |
| 衡量与增长 | 如何定义指标、设计实验、解释结果和停止测试 | 衡量与增长 |

每篇文章应有一个主要搜索/用户意图、原创结论或实操过程、清晰来源、适用边界、相关工具和一条自然的下一步。文章与工具是多对多关系；避免大量只改标题和关键词的模板化正文。

## 6. 工作流专题与服务落地页

### 工作流专题页

每个专题解释业务结果、适用条件、工具顺序、所需资料、预计交付物、证据要求、停止条件和完成后的选择。专题页可以引导免费自助使用，也可以连接相应服务，但不能隐藏工具箱的独立可用入口。

### 服务落地页

落地页按结果和服务范围组织，例如品牌定位、GTM、内容增长、SEO 审计、营销漏斗诊断和销售赋能。每页至少说明：

- 购买者、适用对象和不适用对象；
- 当前问题与预期交付物；
- 使用的工作流和核心工具；
- 客户需提供的资料与决策参与者；
- 范围、时间、验收、例外和停止条件；
- 价格是已批准价格、范围报价还是仍待确认；
- 案例和效果数据的来源与授权状态。

## 7. 公开目录契约

主站和工具箱只共享版本化的公开目录，不共享运行数据。最低记录建议为：

```json
{
  "schema_version": 1,
  "tool_id": "stable-tool-id",
  "title": "Tool title",
  "tier": "core",
  "category": "strategy",
  "tool_url": "https://<toolbox-host>/<tool-path>",
  "marketing_url": "https://modiqi.com/tools/<tool-slug>/",
  "workflow_ids": ["workflow-id"],
  "content_status": "planned",
  "review_status": "unreviewed",
  "updated_at": "2026-08-13"
}
```

约束：

- `tool_id` 一经公开不得因标题变化而变化；
- `tool_url` 和 `marketing_url` 分开，且发布前验证可达与 canonical；
- `content_status` 区分 `planned`、`draft`、`review`、`published`、`retired`；
- `review_status` 区分内容发布与方法审阅，不能互相替代；
- 目录可由 WordPress REST API 或版本化静态 JSON 消费，但任一系统故障不得破坏另一系统核心功能；
- 破坏性字段变化提升主版本，并保留旧消费者迁移期。

## 8. 导航和转化原则

工具箱返回主站的入口应有帮助且不干扰工作：

- 工具箱首页：品牌与服务总入口；
- 帮助或方法说明：对应资源页；
- 工作流完成：相关专题和服务；
- 导出或报告完成：实施、复核或咨询服务；
- 错误与不适用状态：替代工具或人工帮助。

禁止在输入过程中使用强制弹窗、遮挡画布或以提交项目数据换取基本导出。服务 CTA 应标识将离开工具箱，并保持用户本地数据不被自动传输。

## 9. 测量模型

### 事件字典候选

| 事件 | 发生位置 | 最低属性 | 禁止属性 |
|---|---|---|---|
| `resource_view` | 主站资源页 | `tool_id`、tier、referrer class | 画布内容、个人资料 |
| `tool_open` | 工具箱入口 | `tool_id`、source、campaign | 输入字段值 |
| `workflow_start` | 工具箱 | `workflow_id`、source | 项目名称、证据陈述 |
| `workflow_progress` | 工具箱 | `workflow_id`、匿名阶段 | 工具答案、业务机密 |
| `export_complete` | 工具箱 | output type、tool/workflow id | 导出文件或内容 |
| `service_return` | 工具箱到主站 | context、tool/workflow id | 本地项目数据 |
| `lead_submit` | 主站 | service id、consent version | 未经同意的工具数据 |

事件规范必须记录版本、触发条件、去重规则、允许属性、保留期和负责人。跨域测量使用受控链接参数或经批准的匿名标识；UTM 只描述来源与活动，不携带客户、项目或画布字段。

### 漏斗指标

1. 内容合格访问：进入正确问题或资源页；
2. 工具激活：打开目标工具并产生首个有效交互；
3. 工作流推进：完成满足规则的步骤，而非仅点击勾选；
4. 交付成果：完成合格导出或报告；
5. 服务意向：从相关语境进入服务页；
6. 合格线索：由服务团队按购买者、问题、范围和时间确认；
7. 项目与复购：真实合同和交付系统中的业务事实，不能由网页事件推定。

匿名事件只能说明行为，不能证明用户获得业务结果。真实转化、客户项目和复购必须由获授权的业务真源核对。

## 10. 隐私、同意与安全

- 默认不采集画布字段、证据陈述、导出内容、项目名称或客户资料；
- 分析脚本、Cookie、跨域标识和广告像素必须符合实际地区的同意要求；
- 同意前只运行必要功能，拒绝分析不得影响工具使用；
- 隐私说明应区分主站提交数据、工具箱本地数据和匿名测量数据；
- 线索表单仅收集完成服务资格判断所需字段，并声明用途、保留期和删除方式；
- 错误日志和支持附件在发送前提示可能包含业务资料；
- 不将用户导出、截图或报告自动变成案例、训练材料或内容研究样本。

## 11. 内容运营流程

```mermaid
flowchart LR
  A["问题 / 搜索 / 支持证据"] --> B["内容 brief"]
  B --> C["领域与事实审阅"]
  C --> D["编辑、内链和结构化数据"]
  D --> E["发布审批"]
  E --> F["索引、使用与转化观察"]
  F --> G["更新、合并、noindex 或退役"]
```

每条内容记录至少包含 owner、reviewer、source refs、关联 `tool_id`/`workflow_id`、目标意图、状态、canonical、首次发布、最近复核和下次复核日期。内容变更不得直接改写工具方法真源；方法变化先进入核心工具合同和领域评审，再同步公开说明。

## 12. 首批建设顺序

1. 确认工具箱公开主机、主站现有 URL 和跨域隐私边界；
2. 建立 144 条公开目录记录，全部以 `planned` 起步；
3. 完成 6 个工作流专题模板和 30 个核心资源页模板；
4. 优先发布已有 `fixture` 或领域审阅证据的核心页；
5. 以 6 个问题集群制作首批 20–30 篇深度内容，而非批量生成 114 篇；
6. 建立事件字典、同意策略、测试流量排除和跨域验证；
7. 观察至少一个完整评审周期后，再决定扩展工具晋级与付费获客。
